CPD deployment and update workflow

This page describes the intended operational deployment on a Linux service node in the CPD. The aim is to make updates boring: pull the repository, rebuild the image, restart services and run a small health check.

What this deployment is trying to achieve

The CPD machine should behave like a service node, not like a developer laptop. The repository provides the application code and Docker definitions. The node provides the mounted data paths, environment file and private configuration. Keeping those responsibilities separate makes updates repeatable and makes rollback possible when a new version behaves badly.

The normal update path should not involve editing files inside containers, manually installing Python packages, or copying scripts by hand. If the service needs a change, it should be committed to Git, pulled on the node and deployed through the compose file.

Deployment principles

  • The production node should run from a clean clone of the repository.
  • Secrets and local paths stay outside Git.
  • Updates should be limited to git pull, rebuild, restart and health checks.
  • RAW data is mounted read-only; generated products are mounted read-write.

The repository should contain code, Docker definitions and public documentation. The CPD node should contain environment files, mounted data paths and secrets.

Recommended server layout

/opt/gfat-worker/
  repo/                 git clone of gfat-worker
  env/.env.production   production environment file
  secrets/info_scc_user.yml

This layout is only a recommendation, but it encodes an important idea: the repository can be deleted and cloned again without losing the machine-specific environment or secrets. That matters when moving the service to another node or recovering from a broken working tree.

Before installing

Check the node before cloning the repository. It is easier to solve system-level problems before Docker services are involved. 

docker --version
docker compose version
git --version
ssh -T git@github.com

The final command should authenticate against GitHub with the SSH key configured for the service node. If it fails, fix SSH access before continuing; otherwise git pull during updates will fail too.

Initial installation

sudo mkdir -p /opt/gfat-worker/{env,secrets}
cd /opt/gfat-worker
git clone git@github.com:jabravoaranda/gfat-worker.git repo
cd repo
cp .env.example /opt/gfat-worker/env/.env.production

Edit /opt/gfat-worker/env/.env.production with the real CPD paths and service settings.

Keep this file out of the repository. It is specific to the machine where the service runs and may contain paths or operational settings that do not belong in Git.

Prepare local files and mounts

The compose file expects host paths to exist before services start. Create or verify them explicitly, and check permissions with the same user that will run Docker. 

test -d /path/to/RAW/UGR
test -d /path/to/PRODUCTS/UGR
test -f /opt/gfat-worker/secrets/info_scc_user.yml

RAW should normally be mounted read-only inside the container. PRODUCTS must be writable because tasks create output files there. SCC config is mounted read-only and should never be committed to the repository.

Required environment

VariablePurpose
RAW_UGR_HOST_PATHHost path containing RAW input data.

After editing the file, inspect the resolved compose configuration. This catches missing variables and wrong paths before containers are started. 

docker compose --env-file /opt/gfat-worker/env/.env.production \
  -f compose.prod.yml config

Start production services

docker compose --env-file /opt/gfat-worker/env/.env.production \
  -f compose.prod.yml up -d --build api worker redis

After startup, check that all services are up and that the API responds. The exact URL depends on API_PORT. 

docker compose --env-file /opt/gfat-worker/env/.env.production -f compose.prod.yml ps
curl -fsS http://127.0.0.1:<API_PORT>/

First operational checks

Start with a task that does not require real data. This proves that API, Redis and worker can communicate before scientific processing is tested. 

curl -fsS -X POST http://127.0.0.1:<API_PORT>/task_queue \
  -H "Content-Type: application/json" \
  -d '{"task_name":"tasks.misc.test_sum","args":[5,10],"kwargs":{}}'

Then run the LIDAR backend diagnostic. This confirms that the production image can import atmolidarpy as lidarpy. 

curl -fsS -X POST http://127.0.0.1:<API_PORT>/task_queue \
  -H "Content-Type: application/json" \
  -d '{"task_name":"tasks.misc.lidar_backend_status","args":[],"kwargs":{}}'

Use the returned task id with GET /task_queue/{task_id}. A healthy LIDAR backend result should include "backend": "lidarpy".

Update after a repository change

cd /opt/gfat-worker/repo
git pull --ff-only
./scripts/deploy.sh /opt/gfat-worker/env/.env.production

The deployment script is meant to encode the normal update routine. If a manual command is needed repeatedly on the CPD node, add it to the script or document it here instead of relying on memory.

Suggested update checklist

  1. Confirm that the new commit has passed GitHub Actions.
  2. Connect to the CPD node and go to /opt/gfat-worker/repo.
  3. Run git pull --ff-only.
  4. Run the deploy script with the production environment file.
  5. Check docker compose ps.
  6. Submit tasks.misc.test_sum.
  7. Submit tasks.misc.lidar_backend_status.
  8. Only then run a real data task.

Operational commands

docker compose --env-file /opt/gfat-worker/env/.env.production -f compose.prod.yml ps
docker compose --env-file /opt/gfat-worker/env/.env.production -f compose.prod.yml logs -f api worker
docker compose --env-file /opt/gfat-worker/env/.env.production -f compose.prod.yml --profile ops up -d flower

Rollback

Use a known-good Git revision, rebuild and restart the services.

git checkout <known-good-commit>
./scripts/deploy.sh /opt/gfat-worker/env/.env.production

A rollback only works cleanly if operational files are outside Git and the product directories are mounted separately. That is why the production layout keeps repository, environment and secrets in different paths.

What to record after the first CPD deployment

Once the service is running on the real node, update this documentation with the site-specific decisions that are safe to publish: service port, non-secret mount conventions, update routine and any known limitations. Keep credentials, private hostnames and sensitive internal paths out of the public repository.
