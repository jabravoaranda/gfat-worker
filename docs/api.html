api usage

Queue tasks and inspect results

The API is intentionally generic. It does not expose one endpoint per scientific product. Instead, the client sends the Celery task name plus positional and keyword arguments.

How to think about the API

The API is a task queue interface. It is not meant to contain all the scientific vocabulary of every instrument. The vocabulary lives in the task name and in the arguments passed to that task. This keeps the HTTP layer small while allowing new modules to be added without redesigning the API.

A client should usually do three things: list or know the task name, post a payload to /task_queue, and poll the returned task id until the task reaches a final state.

Endpoints

MethodPathPurpose
GET/API information.
GET/registered_tasksRegistered Celery tasks.
POST/task_queueQueue a task.
GET/task_queue/{task_id}Task state and result.
DELETE/task_queue/{task_id}Revoke a task.

Queue request

Every task submission uses the same shape. task_name must match a registered Celery task. args is a JSON array for positional arguments, and kwargs is a JSON object for named arguments. 

{
  "task_name": "tasks.misc.test_sum",
  "args": [5, 10],
  "kwargs": {}
}

Use args when the task has a short and stable argument order. Use kwargs when the task has optional parameters or when the payload should be easy to read months later.

Simple curl example

curl -fsS -X POST http://127.0.0.1:8000/task_queue \
  -H "Content-Type: application/json" \
  -d '{"task_name":"tasks.misc.test_sum","args":[5,10],"kwargs":{}}'

The response contains a task id. Use that id with GET /task_queue/{task_id} until the task is finished.

Manual workflow from the API docs

  1. Open the FastAPI documentation page, usually /docs.
  2. Run GET /registered_tasks and confirm the task name exists.
  3. Run POST /task_queue with the JSON payload.
  4. Copy the returned task id.
  5. Run GET /task_queue/{task_id} until the state is final.
  6. If the state is FAILURE, check the worker logs as well as the API response.

How to read task states

StateMeaning
PENDINGThe task is waiting, unknown, or the worker has not reported progress yet.
STARTEDThe worker has started executing the task.
SUCCESSThe task finished and the result field should contain the returned value.
FAILUREThe task raised an exception. Inspect the error and worker logs.

A task can briefly appear as PENDING even when everything is healthy. Persistent PENDING is different: it usually means the worker is not consuming the queue, the task name is wrong, or Redis is not reachable from one of the services.

Choosing between args and kwargs

StyleUse whenExample
argsThe task has two or three obvious arguments and the order is unlikely to change.["alhambra", "2024-09-09"]
kwargsThe task has optional flags, physical parameters or values that should be self-describing.{"site": "ugr", "overwrite": false}

Diagnostic task

Use this before running real LIDAR tasks. It verifies whether the worker can import atmolidarpy as lidarpy and whether known LIDAR systems are visible. 

{
  "task_name": "tasks.misc.lidar_backend_status",
  "args": [],
  "kwargs": {}
}

Expected backend result includes "backend": "lidarpy".

If the result contains "backend": "missing", the worker image does not have the runtime dependency available. Check worker/requirements.txt, rebuild the image and restart the worker.

LIDAR examples

These examples assume that the corresponding RAW data exists in the mounted RAW path and that output paths are writable from the worker container.

Convert RAW to NetCDF

This is the first LIDAR processing task to try with real data because it only depends on local mounted files and the LIDAR backend. 

{
  "task_name": "tasks.lidar.task_nc_convert",
  "args": ["alhambra", "2024-09-09"],
  "kwargs": {}
}

Generate quicklook

Quicklook generation needs an existing converted product and channel or signal information that makes sense for the selected system. 

{
  "task_name": "tasks.lidar.task_quicklook",
  "args": ["alhambra", "1064fta", "0.0", "30000000.0", "2024-09-09"],
  "kwargs": {}
}

Convert to SCC NetCDF

SCC conversion also needs the SCC configuration mounted at /run/secrets/info_scc_user.yml. Keep that file outside Git. 

{
  "task_name": "tasks.lidar.task_convert_scc",
  "args": ["alhambra", 783, "11:30:00", "12:30:00", 20.0, 1013.25, "2024-09-09"],
  "kwargs": {}
}

Recommended order for real LIDAR validation

  1. Run tasks.misc.test_sum to confirm the queue path.
  2. Run tasks.misc.lidar_backend_status to confirm lidarpy.
  3. Run RAW to NetCDF conversion for a known date with available data.
  4. Run quicklook using the converted product.
  5. Run SCC conversion only after local file processing works.

Task names for new modules

A function mrr_backend_status in worker/tasks/mrr.py is queued as tasks.mrr.mrr_backend_status.

A function dcr_backend_status in worker/tasks/dcr.py is queued as tasks.dcr.dcr_backend_status.

For operational clients, prefer storing the exact JSON payloads used for recurring jobs. That makes failures easier to reproduce from the API documentation or from a terminal.
