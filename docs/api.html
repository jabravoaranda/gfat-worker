api usage

Queue tasks and inspect results

The API is intentionally generic. It does not expose one endpoint per scientific product. Instead, the client sends the Celery task name plus positional and keyword arguments.

Endpoints

MethodPathPurpose
GET/API information.
GET/registered_tasksRegistered Celery tasks.
POST/task_queueQueue a task.
GET/task_queue/{task_id}Task state and result.
DELETE/task_queue/{task_id}Revoke a task.

Queue request

Every task submission uses the same shape. task_name must match a registered Celery task. args is a JSON array for positional arguments, and kwargs is a JSON object for named arguments. 

{
  "task_name": "tasks.misc.test_sum",
  "args": [5, 10],
  "kwargs": {}
}

Simple curl example

curl -fsS -X POST http://127.0.0.1:8000/task_queue \
  -H "Content-Type: application/json" \
  -d '{"task_name":"tasks.misc.test_sum","args":[5,10],"kwargs":{}}'

The response contains a task id. Use that id with GET /task_queue/{task_id} until the task is finished.

How to read task states

StateMeaning
PENDINGThe task is waiting, unknown, or the worker has not reported progress yet.
STARTEDThe worker has started executing the task.
SUCCESSThe task finished and the result field should contain the returned value.
FAILUREThe task raised an exception. Inspect the error and worker logs.

Diagnostic task

Use this before running real LIDAR tasks. It verifies whether the worker can import atmolidarpy as lidarpy and whether known LIDAR systems are visible. 

{
  "task_name": "tasks.misc.lidar_backend_status",
  "args": [],
  "kwargs": {}
}

Expected backend result includes "backend": "lidarpy".

LIDAR examples

These examples assume that the corresponding RAW data exists in the mounted RAW path and that output paths are writable from the worker container.

Convert RAW to NetCDF

{
  "task_name": "tasks.lidar.task_nc_convert",
  "args": ["alhambra", "2024-09-09"],
  "kwargs": {}
}

Generate quicklook

{
  "task_name": "tasks.lidar.task_quicklook",
  "args": ["alhambra", "1064fta", "0.0", "30000000.0", "2024-09-09"],
  "kwargs": {}
}

Convert to SCC NetCDF

SCC conversion also needs the SCC configuration mounted at /run/secrets/info_scc_user.yml. Keep that file outside Git. 

{
  "task_name": "tasks.lidar.task_convert_scc",
  "args": ["alhambra", 783, "11:30:00", "12:30:00", 20.0, 1013.25, "2024-09-09"],
  "kwargs": {}
}

Task names for new modules

A function mrr_backend_status in worker/tasks/mrr.py is queued as tasks.mrr.mrr_backend_status.

A function dcr_backend_status in worker/tasks/dcr.py is queued as tasks.dcr.dcr_backend_status.

For operational clients, prefer storing the exact JSON payloads used for recurring jobs. That makes failures easier to reproduce from the API documentation or from a terminal.
