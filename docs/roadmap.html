roadmap

Current improvement plan

This page summarizes the operational priorities. The editable working tracker remains ROADMAP.md in the repository root.

The roadmap is not a wishlist. It is the place to record what must become more reliable before the worker is used more broadly or before new processing modules are added.

Done baseline

  • Repository hygiene: ignored caches, local data and secrets.
  • Runtime moved from gfatpy to atmolidarpy, imported as lidarpy.
  • Fast pytest suite using uv.
  • Docker smoke workflow for API, Redis, Celery and LIDAR backend checks.
  • Production compose file and deployment helper for the CPD node.
  • GitHub Actions workflow that verifies the worker on push to main.

How to decide the next task

Prefer work that reduces operational uncertainty. A small test or a clear deployment check is usually more valuable than adding a new feature that cannot be verified on the service node.

  • If a failure would stop daily operation, document and test it first.
  • If a manual step is repeated, move it into a script or checklist.
  • If a new package is added, include a backend diagnostic task before adding heavy processing tasks.

Testing strategy

  • Fast tests without Docker for imports, adapters, task registration and API models.
  • Docker tests for the actual API, Redis and Celery execution path.
  • Real-data tests for LIDAR/SCC workflows, kept separate from regular CI because of size and credentials.
  • Deployment checks on the CPD node after every operational update.

Real-data tests should remain separate from the fast CI path. They are still important, but they need explicit data management, expected outputs and a policy for credentials or external services such as SCC.

How to update the roadmap

Edit ROADMAP.md for day-to-day decisions and actions. When the public direction changes, mirror the high-level summary here so the documentation site stays useful for new contributors.
