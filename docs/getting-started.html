getting started

Local setup and first checks

This page is for a developer or operator who has just cloned the repository and wants to know whether the basic pieces work. Start with the tests that do not need Docker, then move to the container stack.

What you should have working by the end

After following this page you should be able to run the fast Python tests, start the Docker stack, open the FastAPI documentation page and submit a simple Celery task. That is the baseline before changing LIDAR tasks, adding mrrpropy or deploying to the CPD node.

Requirements

  • Python 3.11.
  • uv.
  • Docker Desktop or Docker Engine with Compose.

The repository uses uv for local Python checks. Runtime dependencies used inside Docker still live in worker/requirements.txt, because the worker image installs them during the image build.

Clone and inspect the repository

Work from a normal clone of the repository. Before changing anything, check that Git sees a clean working tree. 

git status --short
git log --oneline -5

A clean status makes it much easier to tell which files were changed by a test, a documentation edit or a generated artifact.

Run fast tests

uv run pytest -q

These tests check imports, task registration, API models and lightweight behavior. They do not require Docker, NAS mounts, SCC credentials or real data, so they should be the first check after most code changes.

Expected result:

17 passed

If these tests fail, fix them before starting Docker. They are cheaper to run and usually point to basic issues such as imports, task registration or API model changes.

Run the Docker smoke test

.\scripts\smoke_docker.ps1

This is a small end-to-end check. It starts Redis and the worker/API stack, queues tasks.misc.test_sum, checks the result and removes the test stack. It proves that Celery can receive work through Redis and that the API can report the result.

It is deliberately not a full scientific validation: it does not mount the NAS, does not contact SCC and does not process large LIDAR files.

Use this test after changing Dockerfiles, runtime dependencies, Celery configuration or anything that affects API-worker communication.

Start the development stack

docker compose up --build

Use this when you want to interact with the API manually. After the stack starts, open the automatically generated FastAPI documentation at: 

http://localhost:8000/docs

The interactive API documentation is the easiest way to learn the request format. It also avoids guessing endpoint names while the service is still evolving.

Start the test stack

docker compose -f docker-compose.test.yml up --build

The test compose file avoids clashing with the default development ports. That is useful when you already have another API or Redis instance running.

Default ports:

ServicePort
API18000
Redis6380
Flower5555

First task to try manually

Open http://localhost:18000/docs when using the test stack, or http://localhost:8000/docs when using the default stack, and submit: 

{
  "task_name": "tasks.misc.test_sum",
  "args": [5, 10],
  "kwargs": {}
}

A successful result should eventually contain 15. If this works, the API, broker and worker are talking to each other.

Second task to try: LIDAR backend diagnostic

After the generic queue path works, check that the worker image can import the current LIDAR backend. 

{
  "task_name": "tasks.misc.lidar_backend_status",
  "args": [],
  "kwargs": {}
}

A healthy result should include "backend": "lidarpy". If it reports "missing", rebuild the Docker image and check that atmolidarpy is present in worker/requirements.txt.

Common local problems

SymptomLikely causeWhat to do
Docker cannot bind a port.Another stack is already running.Use the test compose ports or stop the conflicting service.
API works but task stays pending.The worker is not running or cannot reach Redis.Check compose status and worker logs.
LIDAR backend is missing.The image was built before the dependency was added.Rebuild with docker compose up --build.
Fast tests fail but Docker starts.The local Python environment and Docker image are testing different surfaces.Fix the fast tests first; they protect task registration and API models.
