adding tasks

Implement new processing modules

Use this workflow for packages such as mrrpropy, dcrpy, or any other Python processing library.

A task is the boundary between the generic worker infrastructure and one concrete scientific workflow. The worker should not reimplement the science done by packages such as mrrpropy, dcrpy or lidarpy. Its job is to receive a clear request, prepare paths and configuration, call the package, and return a result that an operator can understand through the API.

Before writing code

Start by describing the operation as if it were going to be run by another person from the API. This prevents the task from becoming a hidden script with implicit assumptions.

QuestionExample answer
What package owns the scientific logic?mrrpropy creates a daily MRR product.
What arguments should the API receive?site and date.
Where are input files?Under the RAW mount, for example /mnt/RAW/UGR.
Where are products written?Under /mnt/PRODUCTS/UGR.
Does it need credentials?No for a local product; yes if it uploads to an external service.
How will success be checked?The task returns created files and the output directory contains the product.

Treat the API payload as part of the interface. Once operational scripts start using tasks.mrr.create_daily_product, renaming it or changing argument order becomes a breaking change.

Recommended implementation path

Add the smallest useful task first: usually a backend diagnostic. Once the package import and task registration are verified, add the real data processing task. This keeps failures easier to locate.

  1. Add the package to the Docker runtime dependencies.
  2. Add a backend adapter that imports the package and reports useful errors.
  3. Add a diagnostic task that can be run without real data.
  4. Register the task module in Celery.
  5. Add fast tests for registration and diagnostics.
  6. Add the real processing task with explicit inputs and structured output.
  7. Document the API payload and operational assumptions.

1. Add the dependency

# worker/requirements.txt
mrrpropy==0.1.0
dcrpy==0.1.0

Dependencies needed by Celery tasks must be installed inside the worker image. For that reason they go in worker/requirements.txt. Pin versions for production so a rebuild on the CPD node does not silently install a different scientific library.

Use pyproject.toml for development-only tooling such as pytest. Use worker/requirements.txt for anything the Docker worker must import at runtime.

2. Add a backend adapter

A backend adapter is a small module that centralizes imports and human-readable error messages. It is useful when the package name, distribution name or optional dependency behavior can be confusing. The existing LIDAR code uses this pattern because the PyPI distribution is atmolidarpy but the import package is lidarpy. 

# worker/mrr_backend.py
try:
    import mrrpropy
except ImportError as exc:
    mrrpropy = None
    IMPORT_ERROR = exc
else:
    IMPORT_ERROR = None


def require_mrrpropy():
    if mrrpropy is None:
        raise RuntimeError(
            "MRR processing requires the 'mrrpropy' distribution. "
            "Add it to worker/requirements.txt and rebuild the worker image."
        ) from IMPORT_ERROR
    return mrrpropy

The adapter should not run heavy processing. It should only make the backend available and fail early with a clear message when the runtime image is incomplete.

3. Create the task module

Put task modules under worker/tasks/. Keep the Celery task focused on orchestration: validate arguments, resolve paths, call the scientific package and summarize the result. The task can be thin; the package should own the domain logic. 

# worker/tasks/mrr.py
from celery import shared_task

from mrr_backend import require_mrrpropy


@shared_task
def mrr_backend_status():
    mrrpropy = require_mrrpropy()

    return {
        "backend": "mrrpropy",
        "module": mrrpropy.__name__,
    }


@shared_task
def create_daily_product(site: str, date: str):
    mrrpropy = require_mrrpropy()

    # Replace this block with the real package call once the input and output
    # conventions are agreed.
    product = mrrpropy.create_daily_product(site=site, date=date)

    return {
        "status": "ok",
        "site": site,
        "date": date,
        "created_files": [str(path) for path in product.created_files],
        "errors": [],
    }

The public Celery task name is:

tasks.mrr.mrr_backend_status

and the real product task would be queued as:

tasks.mrr.create_daily_product

This name is what API clients will send in task_name. Keep it stable once other scripts or operators depend on it.

4. Register the module

Celery only exposes modules listed in worker/app.py. Adding a file under worker/tasks/ is not enough. 

# worker/app.py
app.autodiscover_tasks([
    "tasks.lidar",
    "tasks.misc",
    "tasks.mrr",
], force=True)

After this change, /registered_tasks should include the new task names once the API and worker are rebuilt.

5. Design the API payload

The payload should contain operationally meaningful values, not local developer paths. Prefer stable concepts such as site, date, channel, product type or processing mode. Let the task translate those values into mounted paths inside the container. 

{
  "task_name": "tasks.mrr.create_daily_product",
  "args": ["ugr", "2026-05-06"],
  "kwargs": {}
}

If a task has many options, prefer kwargs so the request is self-describing: 

{
  "task_name": "tasks.mrr.create_daily_product",
  "args": [],
  "kwargs": {
    "site": "ugr",
    "date": "2026-05-06",
    "overwrite": false
  }
}

6. Add fast tests

Fast tests should fail before Docker is involved. They should confirm that the task is registered and that the diagnostic path gives a useful result. They should not require the NAS, SCC credentials or heavy real files. 

# tests/test_registered_tasks.py
expected_tasks = {
    "tasks.misc.test_sum",
    "tasks.mrr.mrr_backend_status",
    "tasks.mrr.create_daily_product",
}

Run:

uv run pytest -q

Add Docker or real-data tests only when the task has enough behavior to justify them. The normal sequence is fast test first, Docker smoke test second, controlled real-data test third.

7. Return structured results

Structured results are easier to show through the API, compare in tests and consume from future dashboards. Include enough information for an operator to know what happened without opening the worker logs. 

return {
    "status": "ok",
    "message": "MRR product created.",
    "created_files": [output_path.name],
    "skipped_files": [],
    "errors": [],
}

Avoid returning only free-form strings for new tasks. A message such as "done" is not enough for operation. Return which site, date, files and warnings were involved.

8. Document the task for operators

The task is not finished when the code works locally. It also needs enough documentation for another person to run it, understand the result and know what to check when it fails.

  • Package and version required in the worker image.
  • Task name used in /task_queue.
  • Required arguments and their format.
  • Input file naming convention and mounted path.
  • Output directory convention.
  • Whether the task contacts external services.
  • Expected successful result.
  • Common failure messages and likely causes.

Common failure modes

SymptomLikely causeWhat to check
Task is missing from /registered_tasks.The module was not added to app.autodiscover_tasks.Check worker/app.py and rebuild the container.
Import fails in Docker but works locally.The package was installed in the local uv environment but not in the worker image.Check worker/requirements.txt and rebuild.
Task stays PENDING.The worker is not running, cannot reach Redis, or the task name is wrong.Check worker logs, Redis service and the exact task name.
Input files are not found.The host path is not mounted where the task expects it.Check compose volumes and environment variables.
SCC or external upload fails.Credentials or remote service configuration are missing.Check mounted secret files and keep them outside Git.

Do not put site-specific secrets, absolute CPD paths or test data files in the task module. Pass them through environment variables, mounted paths or external config files.

Review checklist before merging

  • The dependency is pinned in worker/requirements.txt.
  • The task module is registered in worker/app.py.
  • The API payload is documented with a real example.
  • The task returns a structured result.
  • Fast tests pass with uv run pytest -q.
  • Docker has been rebuilt if a runtime dependency changed.
  • Secrets, local paths and real data are not committed.
