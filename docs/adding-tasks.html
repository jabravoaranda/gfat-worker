adding tasks

Implement new processing modules

Use this workflow for packages such as mrrpropy, dcrpy, or any other Python processing library.

A task is the boundary between the generic worker infrastructure and a specific scientific package. The goal is to keep each module small, explicit and testable, while leaving heavy processing inside the package that already knows the domain.

Implementation checklist

  1. Add the runtime dependency to worker/requirements.txt.
  2. Create a task module under worker/tasks/.
  3. Register the module in worker/app.py.
  4. Add tests for imports and task registration.
  5. Document inputs, outputs, mounts and environment variables.

1. Add the dependency

# worker/requirements.txt
mrrpropy==0.1.0
dcrpy==0.1.0

Pin production versions. Do not install packages dynamically every time the container starts.

Use pyproject.toml for development-only tooling such as pytest. Use worker/requirements.txt for anything the Docker worker must import at runtime.

2. Create the task module

Put tasks under worker/tasks/. Keep the task function focused on orchestration: parse arguments, call the scientific library, collect outputs and return a structured result. 

# worker/tasks/mrr.py
from celery import shared_task


@shared_task
def mrr_backend_status():
    import mrrpropy

    return {
        "backend": "mrrpropy",
        "module": mrrpropy.__name__,
    }

The public Celery task name is:

tasks.mrr.mrr_backend_status

This name is what API clients will send in task_name. Keep it stable once other scripts or operators depend on it.

3. Register the module

# worker/app.py
app.autodiscover_tasks([
    "tasks.lidar",
    "tasks.misc",
    "tasks.mrr",
], force=True)

4. Prefer backend adapters for optional packages

A small backend adapter gives clearer errors when a package is missing. It also gives you one place to handle import-name differences, version checks or future compatibility logic. 

# worker/mrr_backend.py
try:
    import mrrpropy
    MRR_BACKEND = "mrrpropy"
except ImportError:
    MRR_BACKEND = "missing"

    def _missing(*args, **kwargs):
        raise RuntimeError("MRR processing requires the 'mrrpropy' distribution.")

5. Add tests

Start with fast tests that do not need Docker. They should confirm that the task is registered and that the backend diagnostic gives a useful response. Add heavier tests later for real files and CPD mounts. 

# tests/test_registered_tasks.py
expected_tasks = {
    "tasks.misc.test_sum",
    "tasks.mrr.mrr_backend_status",
}

Run:

uv run pytest -q

6. Return structured results

Structured results are easier to show through the API, compare in tests and consume from future dashboards. Include enough information for an operator to know what happened without opening the worker logs. 

return {
    "status": "ok",
    "message": "MRR product created.",
    "created_files": [output_path.name],
    "skipped_files": [],
    "errors": [],
}
Avoid returning only free-form strings for new tasks. Structured results are easier to inspect through the API and safer for future dashboards.

Operational documentation per task

Each new module should document:

  • required package and version
  • required mounts and environment variables
  • input file naming convention
  • output directory convention
  • whether it contacts external services
  • example JSON payload for /task_queue

Recommended shape for a real task

@shared_task
def create_daily_mrr_product(site: str, date: str):
    # 1. Resolve input and output paths from configured mounts.
    # 2. Validate that the expected input files exist.
    # 3. Call mrrpropy with explicit arguments.
    # 4. Write products under /mnt/PRODUCTS/UGR.
    # 5. Return a structured summary.
    return {
        "status": "ok",
        "site": site,
        "date": date,
        "created_files": [],
        "errors": [],
    }

Do not put site-specific secrets, absolute CPD paths or test data files in the task module. Pass them through environment variables, mounted paths or external config files.
