architecture

Service boundaries and module layout

The service separates three concerns: accepting task requests, storing those requests until a worker can run them, and executing Python processing code in a controlled environment.

High-level idea

gfat-worker is an execution layer. It does not try to be the scientific library for every GFAT instrument. Instead, it gives those libraries a consistent operational environment: a Docker image, a task queue, an API, mounted data paths and a predictable way to inspect results.

This separation matters because operational processing has different failure modes from library development. A scientific function can be correct and still fail operationally if the dependency is missing in the container, the input mount is wrong, Redis is down or a task name is not registered.

Runtime components

ComponentRole
FastAPIReceives HTTP requests, validates the task payload and asks Celery to queue the task.
RedisStores queued work and task results. It is the communication layer between the API and workers.
Celery workerImports the registered task modules and runs the Python functions in the container.
Celery BeatCreates periodic tasks when scheduled operation is enabled.
FlowerOptional UI for inspecting Celery queues and task history during operation.

Request lifecycle

1. A user or script sends JSON to POST /task_queue.
2. FastAPI validates the payload and calls Celery.
3. Celery writes the task message to Redis.
4. A worker reads the message, imports the task and executes it.
5. Celery writes the state and result back to Redis.
6. The user reads the state with GET /task_queue/{task_id}.

This design allows the HTTP request to return quickly. Long scientific processing happens outside the API process, inside the worker.

Why API and worker are separate

The API should be lightweight and responsive. Its job is to validate a request and enqueue work. Scientific processing can take much longer and can fail for reasons related to files, dependencies or external services. Running that work in a separate Celery worker keeps the HTTP interface available while processing continues in the background.

This also makes scaling clearer later. If task volume grows, more worker processes can be added without changing the API contract. If API traffic grows, the API can be handled separately from the processing workload.

Task registration

Celery task modules are registered in worker/app.py:

app.autodiscover_tasks([
    "tasks.lidar",
    "tasks.misc",
], force=True)

A new module such as worker/tasks/mrr.py must be added to this list as tasks.mrr.

This explicit list is intentional. It keeps task discovery predictable in Docker and in CI. If a task file exists but is not registered here, it will not be available through the API.

Production layout

Production uses compose.prod.yml, where API and worker are separate services built from the same image. Redis persists data in a Docker volume. Flower is optional and only starts with the ops profile.

The API and worker are separate services because they have different operational behavior. The API should stay responsive; the worker may be busy for longer periods while processing data.

FileUseTypical command
docker-compose.ymlDefault local development stack.docker compose up --build

Keeping these files separate avoids mixing local convenience settings with production assumptions. The test compose file also avoids common port conflicts by using ports such as 18000 and 6380.

Tasks should treat these container paths as the runtime interface. Host paths may differ between a laptop and the CPD node, but the container path should remain stable so task code does not need to know where the NAS is mounted on each machine.

Dependency layers

Runtime dependencies go in worker/requirements.txt. Test and development dependencies go in pyproject.toml. Scientific packages needed by tasks must be installed in the worker image.

If a task works locally but fails in Docker, first check whether the dependency was added to worker/requirements.txt. Installing something only in the local uv environment does not make it available inside the worker container.

Architectural rules of thumb

  • Keep task functions thin; call scientific packages for domain logic.
  • Keep secrets and machine-specific paths out of Git.
  • Return structured results instead of free-form strings.
  • Add a diagnostic task before adding a heavy real-data task for a new backend.
  • Verify behavior first without Docker, then with Docker, then with real data.
